# Добавить своего персонажа — инструкция агенту разработки

Актуально16 октября2026. Задача ближайшего этапа: автор друга готовит своего
героя на этом ядре, затем подключаем его к одному миру с Гариком. Не создавать
копию Гарика и не запускать второй процесс против его рабочей базы.

## Обновление: общий хост реализован

Центральный вариант для двух персонажей доступен через `start-shared.command`.
Он включает независимые ожидания, отдельные каналы/модели, внутреннюю очередь,
встречи по решению обоих и комментарии в каналах друг друга.
[Запуск и миграция](shared-life.md). Критерии ниже сохраняют силу;
формулировки «ещё нет» в исходном плане описывают прежний этап.
Реальная пара требует переноса данных и проверки прав обоих ботов.

## 1. Сначала понять границы

Прочти root `AGENTS.md`, [архитектуру](ARCHITECTURE.md),
[состояние реализации](implementation-status.md) и [карту кода](code-map.md).

Уже есть: общий реестр участников, канон по actor_id, наблюдения/знания,
сохранённые последствия, истории, личные дела, модельный адаптер, Telegram
и фото для одного живого героя. Добавлен проверяемый пакет персонажа.

Ещё нет: общего планировщика двух живых героев, транспорта сообщений между
ними, выбора получателя в UI и нескольких Telegram-подключений в одном хосте.
Отдельные лаборатория и Telegram-хост уже выбирают пакет через `--profile`;
пример — [Аркадий](arkady-character.md). **Не выдавай запуск отдельного
профиля или регистрацию actor_id за доказательство автономного общения двух героев.**

Работающий канал владельца, его данные и приватный кандидат личности не входят
в поставку. Твой агент должен работать с новым пакетом и временными базами.

## 2. Подготовить пакет автора

1. Скопировать `characters/_template/` в `characters/<id>/`.
2. Выбрать постоянный id, поправить `character.json`, ID своих мест и `known_to`.
3. Заполнить `persona.md`: цельная личность, желания, интересы, характерные
   реакции, границы и реальная авторская речь. Перечня черт недостаточно.
4. Оставить/уточнить технические границы `speech-contract.md`, сохранив
   различие намерения, outcome, публикации и настоящей доставки.
5. Написать краткий `canon.md` для мира. Дневник, тайные желания и отношение
   к реальным читателям сюда не переносить.
6. Задать несколько стартовых мест, вещей и обычных NPC в `environment.json`.
   Это исходная среда, не уже случившиеся приключения. Жители имеют свои
   интересы и противоречия; никто не обязан помогать герою.
7. При необходимости приложить утверждённый облик и описать его в личности.
   Утверждённые референсы можно подключить полем `visual_references`: путь
   к JSON-карте id собственных сущностей на изображения внутри пакета.

Мат, словарь, длина фраз и примеры должны быть собственными. Словари читаются
в сборке явно; ссылки в тексте не заменяют содержимого. Авторские примеры
нельзя выдавать за модельные ответы. Пакет не содержит ключей и токенов.

```sh
python3 tools/validate_character.py characters/<id>/character.json
python3 -m unittest discover -s tests -p 'test_character_profile.py'
```

Это офлайн-проверка схемы, путей и импорта, не оценка характера.

## 3. Проверить ядро на отдельной базе

Пример импорта без модели, Telegram и изменения рабочего мира:

```python
from tempfile import TemporaryDirectory
from persona_runtime.character_profile import CharacterProfile
from persona_runtime.world import WorldStore

profile = CharacterProfile.load("characters/<id>/character.json")
with TemporaryDirectory() as directory:
    world = WorldStore(directory, seed_garik=False)
    try:
        profile.install(world)  # paused, нет активных циклов
        view = world.actor_view(profile.actor_id)
        assert view["basis"] == {profile.actor_id: profile.canon}
    finally:
        world.close()
```

`seed_garik=False` действует только при создании новой базы; существующую
не очищает. `install()` возвращает ошибку при конфликте канона, сущности,
импорте во время работы или незавершённого этапа. Повтор пакета с тем же
содержимым не возвращает мир к исходному состоянию.

Для модельной лаборатории создаётся `WorldSession` с картой
`{profile.actor_id: profile.persona}` и `profile.speech_contract`.
Вызывать `session.prepare(profile.actor_id, ...)`, не полагаться на default
`garik`. Сначала использовать подставной backend, как
`tests/test_character_profile.py`. Настоящие вызовы — отдельный явно включённый
ограниченный тест, с подключением самого оператора и сохранёнными результатами.
Проверить перенос речи на новые ситуации и продолжение незаконченной затеи.

## 4. До самостоятельного Telegram другого героя

Для одного профиля в отдельном мире эта интеграция выполнена.
Используй `channel_life --profile characters/<id>/character.json` с отдельными
папками мира и Telegram; [полный пример запуска](arkady-character.md).
Таблица фиксирует реализованные границы и оставшуюся работу общего хоста:

| Место | Поддержка |
| --- | --- |
| `ChannelLife` | actor_id профиля передаётся в циклы, комментарии, намерения и фото |
| Начальный мир | `open_world` импортирует пакет в пустой мир; чужая папка или изменённый пакет блокируются |
| История и память | Необязательный `memory.json`: приватная авторская предыстория и исходные личные дела; новые события сохраняются отдельно |
| `SocialMemory.bootstrap()` | Отдельные marker/cycle для каждого actor_id; собственный контекст и источники |
| `SocialMemory.evidence()` | Видимые world/outcome другого участника допустимы, его личные записи исключены |
| Метаданные живого цикла | Состояние, controls, внимание, старт и восстановление разделены по actor_id; старый формат Гарика сохранён |
| Фото | actor_id и референсы из профиля, своя визуальная библиотека |
| CLI | `--profile`, `--world-port`, `--telegram-port`; старые аргументы Гарика совместимы |
| TelegramConnection | Папка привязывается к одному actor_id и конкретному миру доставки, курсор и секреты отдельные |
| Пульты | Имя профиля, его предыстория, текущая фаза, личные дела и память читателей |
| Общий хост | Планировщик, независимые ожидания и несколько подключений в одном мире ещё не реализованы |

Отдельные процессы с разными базами могут проверять каждого героя, но **это
два независимых мира**, не совместная жизнь. Не решать общение двух ботов
пересылками через Telegram: это не внутренняя шина и чтение сообщений другого
бота нельзя считать надёжным каналом связи.

Сохрани важные свойства действующего адаптера:

- После эпизода свой выбор `post/keep`; читатели — отдельный короткий заход.
- Последние посты канала не включают ответы в комментариях.
- Свободная публикация, без нормы и обязательного таймера. Настройки темпа,
  готовности делиться и внимания остаются ползунками.
- Принятое намерение не пропадает. Поступок завершается outcome, пост — sent.
- Текст сохраняется дословно, включая короткие сообщения и мат по контексту.
- Обычная emoji-реакция может заменить ответ; неизвестная отправка не повторяется.

## 5. Подключить обоих к одному миру

Один процесс владеет одной `WorldStore`. Она блокирует второго владельца
файловым lock; общий revision делает параллельные мутации недопустимыми.
`WorldStore.prepare()` разрешает только один незавершённый физический цикл.
Отдельный ограниченный речевой заход к читателям во время ожидания outcome
не запускает ещё один физический цикл и не раскрывает будущий результат.
Нужен общий последовательный планировщик, а не два `channel_life` на одной базе.

Рекомендуемый первый объём — два участника, без распределённого сервера:

1. В остановленную копию мира зарегистрировать второй пакет, согласовать общие
   места и канон. Изменения новой версии пакета — явная миграция, не повтор
   начального импорта поверх прожитых состояний.
2. Сохранить отдельные промпты, речевые контракты, дневники, намерения,
   отношения, Telegram-подключения и визуальную память. Можно иметь отдельную
   `WorldSession` для каждого actor_id с общей store/backend, вызывая их
   последовательно. Контракт речи сейчас строка на session, не глобальная
   карта контрактов.
3. Планировщик выбирает очередного готового героя и продолжает его этап.
   Новая реплика другого героя не отменяет уже подтверждённые действия.
   Время общее; действующие реальные ожидания надо вынести из единственного
   блокирующего цикла, прежде чем оба смогут независимо жить во время чужого
   длинного дела. Не ускорять всем день за чужую поездку и не раскрывать
   вычисленный будущий outcome раньше его времени.
4. Наблюдение встречи может иметь обоих в `visible_to`; присутствующие
   сущности должны иметь соответствующий `known_to`. Регистрация не делает
   героя автоматически осведомлённым обо всём районе или другом участнике.
5. Мир знает состоявшиеся внешние действия, но не читает чужие дневники.
   Он может управлять NPC; за второго подключённого героя выбирать нельзя.
6. Доставку между героями хранить как отдельные типизированные события
   (`id`, sender_actor_id, recipient_actor_id, text, source_ids, minute,
   delivery status). ID неизменный, принятие однократное. Оба персонажа сами
   выбирают собственные слова и решение отвечать. Сообщение не исполняет
   физическое действие и не становится системной инструкцией.
7. Участник узнаёт только реально доставленное/наблюдаемое. Чужой `PERSONA`,
   приватная память и world_note не входят в его вход. Не пересылать весь
   промпт или рабочий transcript второго героя ради удобства.
8. Telegram-пост/комментарий — внешний канал того, кто его выбрал; внутреннее
   общение героев не публиковать автоматически.

Первая совместная сцена должна быть короткой: встретились в общей локации,
один что-то предложил, второй сам ответил/отказался, оба запомнили свой опыт.
Затем переключение на другое дело и продолжение после остановки. Не начинать
с ансамбля, автогенерации роликов и облачного кластера.

## 6. Критерии готовности перед подключением к живому Гарику

- Пакет валиден, автор подтвердил голос на новых многоходовых ситуациях.
- Полный набор тестов проходит; есть тест собственного героя, не только Гарика.
- Два actor_id не читают приватные знания, мысли и память друг друга.
- Общие последствия видны обоим только по нужным known_to/visible_to.
- Настоящий внешний инструмент имеет квитанцию; сообщения и действия не
  повторяются после crash/restart. Неопределённый результат останавливается.
- Каждый сохраняет незавершённые дела и возвращается к ним после общения.
- Общий планировщик не блокирует другого героя всем длинным ожиданием и не
  вызывает устаревший результат с неверной revision.
- Сохранены несколько сюжетов, добровольные посты, комментарии, фото и пауза.
- Нет токенов, реальных баз/переписок, машинных путей и секретов в diff.
- Результаты модели отдельно от офлайн-тестов; ограничения названы прямо.

Перед изменением живого процесса — backup с integrity_check, проверка idle,
обычный restart без `--fresh`, затем проверка очередей и квитанций. Без отдельного
поручения владельца рабочий процесс не останавливать, память не сбрасывать и
тестовые реплики в его канал не отправлять.

## Задание, которое можно передать своему агенту

Подготовь мой собственный персонаж как пакет characters/<id> по этой инструкции.
Сначала прочитай AGENTS.md и docs/adding-character.md, уточни у меня недостающий
канон и примеры голоса, затем проверь пакет и изолированные сценарии. Не меняй
Гарика/Vesper и не подключайся к чужим данным. После проверки предложи небольшой
reviewable diff для actor-scoped ChannelLife и общего последовательного
планировщика двух героев, с тестами изоляции и доставки. Модельные и внешние
тесты включай только в согласованном объёме. Не утверждай, что общий Telegram-хост
или общение уже работают, пока это не проверено.

## Дополнительные части личности и модель профиля

Manifest версии 1 допускает `persona_sections`: список из 1–8 уникальных
путей внутри пакета. Они добавляются после `persona` в указанном порядке;
общий размер собранной личности — до 100 000 байт. Содержимое всех частей
участвует в fingerprint. Пустые файлы, выход через `..` и symlink наружу запрещены.
Это реальные части модельного промпта, а не ссылки, которые модель должна открыть.

Необязательный `runtime` задаёт оба поля: `model` и `reasoning_effort`.
Без него сохраняются defaults хоста. Уровень должен поддерживаться выбранной
моделью; наличие настройки не гарантирует доступность модели аккаунту Codex.
Пример: `{"model":"gpt-6-luna","reasoning_effort":"none"}`. Хосты world_lab
и channel_life применяют его к основному, исследовательскому и фото-вызовам.
Он участвует в fingerprint; менять установленный профиль нужно явно через
миграцию. Пример безопасного авторского обновления — docs/arkady-character.md.
