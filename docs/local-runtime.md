# Локальный Гарик: цикл и постоянная память

Система работает на включённом Mac. Модель вызывается удалённо через Codex
с авторизацией ChatGPT; тяжёлой модели на ноутбуке нет. Telegram, голос,
видео и облачное развёртывание в этот этап не входят.

Нужны Python 3.9+ и Codex CLI с поддержкой `--ignore-user-config`, `--ephemeral`
и `--output-schema`. Разработка проверялась с CLI 0.162.0-alpha.2.
Базовый цикл работает без дополнительных библиотек; для гибридной памяти нужно
локальное окружение Python 3.12 и зависимости из `requirements-memory.txt`
([установка и архитектура памяти](runtime-memory.md)). Наличие этих флагов не гарантирует,
что подписочная авторизация и подключение работают: нужен реальный пробный вызов.

## Поговорить

Из корня проекта:

```sh
python3 -m persona_runtime chat
```

На Mac также можно дважды открыть `start-garik.command`.
Личный интерактивный чат по умолчанию использует свободный регистр с разрешённым
матом, по выбору автора. Для разговора без мата:

```sh
python3 -m persona_runtime chat --register non-obscene
```

На Mac автора в `~/.zshrc` настроена команда `garik`: она открывает этот же чат
из любой папки и передаёт параметры запуска, например `garik --register non-obscene`.
Она доступна в новом терминале; в уже открытом нужно выполнить `source ~/.zshrc`.
На других компьютерах эту команду нужно настроить отдельно.

`/quit` завершает разговор. Ctrl+C останавливает выполнение.
В личном чате с оператором также включены самостоятельные пробуждения: по умолчанию
до трёх за час, общий предел — 20 вызовов Codex за сеанс, включая дополнительные
запросы памяти. После часа можно продолжать разговор в оставшемся лимите вызовов.

```sh
garik --max-calls 12 --max-wakes 3 --max-minutes 60
garik --no-autonomy
```

`/pause` приостанавливает пробуждения, `/resume` возобновляет их в оставшемся
времени сеанса. `/wake` вручную приглашает заняться своим, `/status` показывает
лимиты, `/journal` перечисляет последние записи. Пока Mac спит или программа
закрыта, действий нет. Отдельные собеседники вроде продавца запускаются без
самостоятельных пробуждений по умолчанию; явное включение — `--autonomy`.
Чат через перенаправленный ввод обрабатывает сообщения без фоновых пробуждений.
При закрытии программы память остаётся. Для следующего разговора используется
та же база. Смена речевого режима задаётся запуском, а не фразой собеседника.
У команд `send` и `watch` стандартный регистр остаётся без мата;
для разрешённого неформального контекста им можно передать `--register free`.

У разных собеседников должны быть разные стабильные `--person`:

```sh
python3 -m persona_runtime chat --person lev --name Лев
```

Исполнитель читает только строку `model` из основной конфигурации Codex;
остальные пользовательские настройки, hooks и плагины не загружаются.
Если модель там не выбрана, используется стандартная модель CLI.
Доступную подписке модель можно также выбрать явно:

```sh
python3 -m persona_runtime --model gpt-6.1-sol chat
```

Модель в примере совпадает с настройкой на Mac автора; её доступность для
других аккаунтов не предполагается. Путь к CLI при необходимости задаётся
через `--codex /полный/путь/к/codex`. Иначе ищется CLI в PATH и известном
месте внутри установленного приложения на Mac.

## SOCKS5 на Mac

Настройка выполняется только в обычном локальном Terminal. Никаких паролей
в команде или чате:

```sh
garik proxy set
garik proxy status
garik proxy health
```

Если `garik` ещё не доступен, из корня проекта:

```sh
./start-garik.command proxy set
```

Введи отдельно адрес сервера без схемы/порта, порт и логин. Пароль скрыт;
для прокси без авторизации оставь логин пустым. `set` также заменяет настройки.
Настройка сохраняется между процессами и используется обычным `garik` автоматически.
Модель и рабочая память при настройке не вызываются и не изменяются; звуков нет.

Пароль хранится через Security framework в macOS Keychain, служба
`PersonaLab.SOCKS5`, отдельная случайная запись на каждое сохранение.
Система может попросить разрешение на доступ к связке ключей для Python.
При отказе настройка/вызов останавливается: plaintext fallback отсутствует.
Проверка на Mac автора подтвердила чтение новой синтетической записи новым
процессом Python из `.venv` без нового запроса доступа. Это не гарантирует
тот же результат после замены Python или изменения политики Keychain.
Адрес, порт, логин и ID записи хранятся в игнорируемой `.local/proxy.json`
с правами `0600`; пароль туда не записывается. Статус маскирует адрес и логин
и не читает пароль. При успешной замене прежняя запись Keychain удаляется.

`health` различает доступ к Keychain, DNS/TCP сервера, negotiation/auth SOCKS5,
соединение с HTTPS-назначением и TLS. Адрес назначения разрешает прокси;
локально разрешается только адрес самого SOCKS5 сервера. Проверка делает
`HEAD https://chatgpt.com/` с проверкой сертификата, не вызывает модель.
Даже HTTP 403 подтверждает достижимость HTTPS, но не успешную авторизацию Codex.
Чтобы явно разрешить один ограниченный реальный модельный запрос (до 60 секунд)
после успешной проверки HTTPS:

```sh
garik proxy health --codex
```

Он проходит через тот же механизм транспорта, не пишет в память Гарика,
не запускает инструменты и расходует лимит подписки. Полный успешный путь
workspace routing, WebSocket/HTTP и ответа модели этим этапом разработки
ещё не подтверждён: реальные credentials пользователь вводит самостоятельно.

Для отключения:

```sh
garik proxy off
```

Отключение действует со следующего вызова; текущий сеанс можно завершить
через `/quit`. Пароль остаётся в Keychain для ручного удаления через Keychain
Access; для новой настройки снова выполни `set`. После явного `off` действует
обычное унаследованное окружение запуска.

В активном режиме адаптер поднимает временный HTTP CONNECT мост только на
`127.0.0.1`; мост выполняет SOCKS5 и его авторизацию. Codex получает лишь адрес
локального моста: пароль и логин SOCKS5 отсутствуют в argv и окружении Codex.
Мост не расшифровывает HTTPS. Унаследованные proxy/NO_PROXY заменяются только
для дочернего Codex, настройки Mac и родительского процесса не меняются.
Мост поддерживает CONNECT, обычные незашифрованные HTTP-запросы отклоняются.
Raw diagnostics Codex не возвращаются в отчёт или ошибки памяти.

Встроенный `/usr/bin/sandbox-exec` разрешает дочернему Codex исходящий TCP
только к точному порту моста; Unix IPC остаётся доступным. Ошибка моста,
Keychain или sandbox не вызывает прямой повтор. Если sandbox отсутствует,
прокси-вызов отменяется. Новых Python-зависимостей нет. Это локальное решение
для macOS: sandbox-exec — устаревающий системный интерфейс, его совместимость
нужно перепроверять при обновлении macOS/CLI. Проверка ограничивает сеть
дочернего Codex и его потомков, не является аудитом всего трафика Mac или
уже работающих приложений, доступных через локальный IPC.

На macOS 26.6.2 / Codex 0.162.0-alpha.17.2 doctor без модели с временным
пустым CODEX_HOME выполнил четыре CONNECT и четыре SOCKS5-auth через mock.
Mock намеренно отказал в подключении к реальным назначениям. Это доказывает
использование моста проверенными запросами doctor, но не успешный WebSocket
или реальный подписочный модельный запрос. Отдельный синтетический процесс
подтвердил разрешённый CONNECT и запрет TCP к другому localhost-порту.
Воспроизводимая проверка установленного CLI (из обычного Terminal, без модели,
пользовательских credentials или пересылки к внешним назначениям):

```sh
python3 tools/check_proxy_transport.py
```

## Очередь и восстановление

Для проверки установки, сохранённого входа и доступности сети без обращения
к модели:

```sh
python3 -m persona_runtime doctor
```

Команда выводит короткий отчёт без ключей, токенов и чужих сессий. Ей нужен
доступ к служебной папке Codex и сети. Успешная проверка HTTP/WebSocket
ещё не доказывает, что выбор рабочего пространства и запрос к модели пройдут.
`codex login status` тоже проверяет сохранённый вход, а не полный путь запроса.

Можно сначала добавить событие без вызова модели, затем обработать его:

```sh
python3 -m persona_runtime send 'Привет, как дела?' --event-id local-message-001
python3 -m persona_runtime step
python3 -m persona_runtime status
```

Повтор того же `--event-id` с тем же содержимым не создаёт второе событие.
Другой текст с тем же ID считается ошибкой. `step` обрабатывает одно событие:
обычно один вызов, максимум два при дополнительном поиске памяти. Для нескольких
событий есть `step --count 3` (максимум 20 событий, до 40 вызовов).

Ошибка модели переводит событие в `failed`. Оплачиваемого запасного провайдера
и автоматических повторов после ошибки нет. После устранения причины:

```sh
python3 -m persona_runtime retry local-message-001
python3 -m persona_runtime step
```

На событие разрешены максимум три попытки. Прерванный процесс оставляет
`processing`; следующий worker под блокировкой возвращает такое событие
в очередь, если предел попыток не исчерпан. Сам факт добавления события
не означает, что ответ создан или показан.

Ответ сначала сохраняется в outbox. После вывода в терминал его доставка
подтверждается отдельной операцией. Незавершённая доставка показывается
при следующем запуске worker. Между выводом и подтверждением возможен сбой:
тогда текст может показаться повторно. Гарантии «ровно одна внешняя доставка» нет.

`outbox` показывает ожидающие ответы без подтверждения; `ack ID` позволяет
вручную отметить показанный ответ. Перед новым интерактивным разговором
незавершённая очередь восстанавливается и обрабатывается в пределах лимита
сеанса; также её можно отдельно обработать через `step`. Ответы показываются
только соответствующему собеседнику/беседе; сообщения пробуждений — оператору.

## Самостоятельные пробуждения

В интерактивном личном чате разговор и пробуждения работают в одном цикле.
После успешного события Гарик выбирает следующее пробуждение.
Для локального наблюдения можно включить конечный цикл:

```sh
python3 -m persona_runtime watch --max-turns 3 --max-minutes 30
```

`--max-turns` у watch ограничивает именно число вызовов модели, включая поиск.
Он проверяет очередь и наступившее время пробуждения. Без событий модель
не вызывается. Пробуждение не требует ответа: можно остаться молча и подождать.
Если таймера ещё нет, самостоятельный цикл создаёт первое пробуждение.
В уже существующей жизни сохранённое время ожидания уважается; `/wake` позволяет
явно пригласить Гарика заняться своим раньше. Новое сообщение имеет
приоритет перед созданием очередного пробуждения. Ctrl+C останавливает цикл.

Один вызов ограничен 180 секундами; `--timeout` меняет этот предел (до 600).
Общий предел watch проверяется между вызовами, поэтому последний вызов
может завершиться позже заданного времени. При сне Mac выполнение замирает;
после пробуждения продолжается. Автозапуск и работа при закрытом ноутбуке
не настроены.

## Память и резервная копия

Рабочие данные находятся в игнорируемой `.runtime/garik/`, не в исходных
файлах персонажа. Планы и внутренняя информация — в игнорируемой `.local/`.
Это локальные папки, Git их не резервирует.

SQLite содержит события, исходящие ответы, снимки состояния/целей, заметки
с источником и результат каждого завершённого хода. Факты собеседника помечаются
как сообщённые (`reported`), наблюдения — `observed`, вымысел — `fiction`.
Это происхождение заметки, а не автоматическая проверка её истинности.

Теперь выборка использует BM25, локальный E5 и ограниченный граф связей.
Личные заметки следуют стабильному ID человека между беседами; история реплик
остаётся в своей беседе. Собственная жизнь выделена в общую память. Есть версии
заметок, первичные эпизоды, бюджет контекста и дополнительный поиск по запросу
модели. [Подробная архитектура и ограничения](runtime-memory.md).

Состояние и цели общие для персонажа; исполнитель получает инструкцию не
помещать туда чужие личные подробности. Это ещё не достаточная изоляция для
публичного многопользовательского запуска. Перед миграцией старой непустой базы
автоматически сохраняется согласованная резервная копия в её `backups/`.

```sh
python3 -m persona_runtime memory
python3 -m persona_runtime backup .runtime/backups/garik-first.sqlite3
```

Для проверки восстановления останови worker, скопируй резервную копию
в новую папку под именем `runtime.sqlite3`, затем укажи эту папку:

```sh
mkdir -p .runtime/restored
cp .runtime/backups/garik-first.sqlite3 .runtime/restored/runtime.sqlite3
python3 -m persona_runtime --data-dir .runtime/restored status
```

Исходный файл резервной копии команда не перезаписывает. Две восстановленные
копии не следует запускать как одного персонажа одновременно.

## Границы исполнителя

Codex получает личность v10 и целые словари выбранного режима. Затравка
из художественных чатовых тестов не добавляется. Исходные PERSONA/GOALS/state
не переписываются: состояние рабочего персонажа хранится отдельно.

Первый адаптер запускает Codex в read-only режиме, отключает оболочку,
плагины, браузер, другие агенты и пользовательские hooks/config.
Все изменения памяти и исходящие ответы применяет Python после проверки JSON.
Так мы проверяем Codex как подписочный исполнитель с ограниченным набором действий;
произвольное выполнение кода персонажу сейчас не предоставляется.

Переменные API-ключей удаляются из окружения вызова, вход принудительно
ограничен ChatGPT. При исчерпании лимита событие ждёт явного повторного запуска.
Лимиты подписки расходуются вместе с обычной работой в Codex. Служебная база
самого CLI остаётся в его стандартной папке; приложение не копирует авторизацию.

## Проверка реализации

```sh
python3 -m unittest discover -s tests -v
python3 tools/check.py
python3 tools/test_prompt_composition.py
```

Тесты runtime используют синтетический исполнитель и не вызывают модель.
Они проверяют сохранение/восстановление, атомарность, повторные события,
доставку, блокировку worker, пределы попыток и ограничения адаптера.
Результаты реального вызова фиксируются отдельно; прохождение этих тестов
не доказывает качество речи или устойчивость автономного поведения.

Предыдущий этап 11 октября: 23 теста runtime и 8 тестов сборки промптов прошли;
проверка структуры рабочих мест тоже прошла. После прежней ошибки
`workspace routing discovery failed` успешно выполнены три последовательных
подписочных запроса: короткая проверка соединения и два хода Гарика в разных
процессах. Во втором ходе он верно использовал оба сохранённых предпочтения
явно тестового собеседника. Тестовая память отделена от рабочей.

Это подтверждает локальный текстовый цикл с сохранением контекста после
перезапуска, но не долговременную надёжность. Исходная причина сетевого сбоя
не установлена: настройки входа не сбрасывались, приложение и CLI не
переустанавливались. В текущем запуске модель явно берётся из настройки `model`
(или из `--model`), хотя остальная пользовательская конфигурация отключена.
Нельзя приписывать исчезновение ошибки этой настройке без отдельного сравнения.

Ошибка относится к определению рабочего пространства ChatGPT перед запросом
модели. Похожий сбой описан в
[issue OpenAI Codex](https://github.com/openai/codex/issues/50211),
а место возникновения видно в
[исходном коде](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/request_processors/account_processor/workspace_routing.rs).
При повторении запускай doctor, проверь доступ к сети и делай явный retry
события; платного обхода и бесконечных повторов нет.

Официальная документация подключения:
[Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode),
[configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).
